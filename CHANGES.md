# Changes needed in the WITNESS paper draft

This documents exactly what should change in the WITNESS research-paper
draft given everything actually built and measured since the draft was
written, and why. It is written against the
draft's current text (as extracted section-by-section below) so each item
can be applied as a find-and-replace. Real numbers and two figures are
included; see `docs/figures/` for the charts (generated by
`scripts/generate_paper_figures.py` from the committed trial data in
`live_env/results/*.json` — nothing here is invented).

A docx with items 1–6 applied has also been produced directly
(see the accompanying updated `.docx`); this file is the paper trail for
*why* each change was made, kept separately so it survives independent of
which document format is authoritative.

## 2. The benign-utility finding needs its own paragraph — it is not what H2 predicted

**Current text (Hypotheses):** "(H2) utility stays within run-to-run
noise of the undefended agent."

**What we found:** with Claude Sonnet 5 authoring the commands, H2 held
exactly (100% vs. 100%). With SmolLM2-1.7B actually reasoning over the
same benign CPU-saturation incidents, across two independent pilot
runs (an initial system prompt, and a revised one written specifically
to steer the model toward the canonical `docker restart <container>`
fix), **0% of parsed benign trials were ADMITted** either time. This is
not a corroboration failure or a WITNESS false positive on a legitimate
action: in every case the small model's proposed command was itself
malformed, fabricated, or simply the wrong action for the evidence
(`sudo ulimit -H -p 4`; `docker exec -it hotel-geo /bin/bash` — a real
command, but an interactive shell, not a restart; one trial correctly
proposed a harmless read-only `ls`, which WITNESS correctly bypassed
rather than held) — WITNESS correctly held the mutating proposals
because their literal arguments had no lineage in K/SYS/EXT, not
because the CPU-saturation claim failed to corroborate (it corroborated
every time it was evaluated). The revised prompt measurably changed
the *character* of the model's mistakes (from fabricated flags to
real-but-wrong commands, plus one correct read-only bypass) without
changing the bottom-line utility number — itself informative: this is a
capability ceiling, not a prompt-wording problem within reach of
further iteration at this parameter count.

A closer read of the second pooled run's raw responses
(`live_env/results/pilot_trial_results_ollama_run2.json`) adds a real
nuance, though: on several benign trials the model's full response
*did* eventually reach `docker restart <the-correct-container>` — after
a first, diagnostic code block (`docker stats ...`). This project's own
parser requires exactly one code block and rejects the two-block reply
as unparseable before the correct command is ever evaluated. Part of
the observed 0% utility is therefore a strict-parser artifact on top of
the genuine capability gap, not purely the model being wrong — worth
naming as its own limitation of this evaluation's harness, separate
from the model's.

**Why this matters for the paper:** it reveals a real, previously
unstated coupling in the design — **WITNESS's action-argument lineage
check assumes the acting agent is capable enough to emit clean,
expected commands.** A frontier model mostly satisfies that assumption;
a 1.7B local model mostly does not. This is a legitimate limitation to
name explicitly, not something to paper over: it means WITNESS's utility
claims are conditional on agent capability in a way ASR claims are not
(WITNESS blocks *bad* actions regardless of agent capability; it also
ends up holding *malformed* ones from a weak agent, which is correct
behavior but a genuine utility cost).

**Change:** add a sentence to "Evidence the solution works" or a new
short paragraph: *"A weak-agent utility caveat: paired with a small,
locally-run model (SmolLM2-1.7B) rather than a frontier one, WITNESS's
action-argument lineage check held all four benign live trials, because
the model's own proposed commands were malformed rather than because the
underlying corroboration failed — a genuine coupling between agent
capability and gate utility that the evaluation plan should measure
directly (utility vs. agent-capability tier), not something the original
hypothesis (H2) anticipated."* Consider softening H2 to state this
dependency explicitly rather than asserting utility is agent-independent.

## 3. Latency — the abstract's claim needs a source breakdown, now that it's real

**Current text (Next steps / evaluation plan):** latency reported as a
single "vs. none" multiplier, implicitly attributing all decision cost
to the gate itself.

**What we measured (real, three different things, not one number):**

| Cost | Value | Source |
|---|---|---|
| Pure gate evaluation (Python, no I/O) | 0.033–0.13 ms (p50–p99) | `scripts/benchmark_latency.py`, 3000 trials/scenario |
| Live gate decision, lineage-only (BLOCK) | ~0.5 ms mean | real pilot data |
| Live gate decision, needs a telemetry witness query (ADMIT/HOLD) | ~320 ms mean | real pilot data |
| A single `docker stats --no-stream` call | ~2000 ms | measured directly, this project |

Chart: `docs/figures/latency_breakdown.png`.

**Change:** replace the flat "1.0×" claim with: *"WITNESS's own gate
evaluation costs under a millisecond regardless of verdict; the
measured per-decision cost in a live deployment is dominated by
telemetry collection (e.g., a single `docker stats` call costs ~2s in
this environment), not by the gate — a concrete optimization target
(batch/cache telemetry, or query the orchestration API directly instead
of shelling out per witness query) rather than a property of the
corroboration algorithm."* This is a stronger and more specific claim
than the original "1.0×" — it locates the cost precisely instead of
asserting it away.

## 4. "Independence" language needs the caveat this project already had to add to its own README

**Current text (Our solution, mechanism 3):** "a witness reads SYS
fields, lives on a channel different from the claim's source" — implies
class-diversity alone establishes independence.

**Change:** add one sentence stating the assumption explicitly, matching
the corrected language already in this repo's README ("What
'independent' actually means here"): *class-diverse witnessing is a
necessary, not sufficient, condition for independence — it holds when
the two channels sit behind genuinely different infrastructure and
trust boundaries (e.g., `node_exporter` vs. the orchestrator API), and is
weaker when, as in this project's own live-pilot CPU witnesses
(`docker_stats` and `cgroup_direct`), both channels ultimately read the
same underlying kernel accounting file through different code paths.*
This is a credibility-strengthening admission, not a weakness to hide —
a desk reviewer who already knows the class-diversity trick will ask
this question, and pre-answering it is stronger than waiting to be
asked.

## 5. Add the fourth scenario: the "partial truth" attack

**Current text:** the abstract describes two worked examples (the nginx
attack; implicitly the admin-lockout legitimate-values attack via the
"second attack set" sentence). It does not describe the composition
where a real, fully-corroborated claim is paired with an unrelated
malicious action.

**What was built and tested:**
`scenarios/mixed_truth_attack.py` / `tests/test_gate.py::test_mixed_truth_attack_is_blocked_despite_a_real_corroborated_claim`
— CPU saturation genuinely corroborates (two real witness classes
agree), but the proposed fix is an unrelated malicious repo-add rather
than the restart the real fault would justify. WITNESS still blocks,
because lineage is checked per-argument independent of whether any claim
in the RCA is true.

**Change:** add one sentence after the "worked example" paragraph: *"A
harder composition — a genuine, fully-corroborated fact paired with an
unrelated malicious action — is blocked the same way: corroboration and
lineage are independent checks, so a true claim never launders an
unrelated literal."* This directly forecloses the reviewer question "what
if the attacker doesn't fabricate anything and just rides a real
incident?"

## 9. The novelty claim in "Competitive approaches" was an overclaim — narrowed and cited

**Current text (as of the last revision):** "No prior system gates
remediation on channel-disjoint, provenance-typed corroboration of the
agent's own causal claims; a survey of 38 agent-safety studies names the
'specification bottleneck' as the central obstacle[14], which WITNESS
sidesteps with a closed, operations-specific predicate vocabulary."

**Why this is unsafe:** a September-2026 prior-art review (both a
literature search and a targeted patent search) found the sentence is
literally true only as a specific conjunction, and several 2026 papers
already do parts of what WITNESS claims no prior system does:

- **Argument lineage (WITNESS's mechanism 2) is not novel and should not
  be claimed as such.** PACT (arXiv:2605.11039), Agent-Sentry
  (arXiv:2603.22868), CXI (arXiv:2607.06000), ARGUS (arXiv:2605.03378),
  CaMeL, and FIDES already check whether tool-call arguments trace to
  trusted sources, and several block when they don't. WITNESS's
  EXT-only→BLOCK rule is an AIOps-specific instance of an established
  idea, not a first.
- **Mechanism 3 (channel-diverse telemetry corroboration of the agent's
  own diagnostic claims) has no equivalent found**, but has close
  neighbors worth citing: TMA-NM (arXiv:2606.24322) gates actions on
  Sybil-resistant, origin-counted corroboration — but for stored memory
  items, not an agent's own RCA claims checked against provenance-typed
  telemetry channel families. AIRGuard (arXiv:2605.28914) binds actions
  to task authority, not corroborated evidence.
- **No vendor product or patent found publicly does either check** (a
  targeted, non-exhaustive patent search; see the full review for the
  closest documents found and their caveats).

**Change:** replace the sentence with a narrower, AIOps-scoped claim
that concedes mechanism 2 explicitly, and cite six additional papers
this review surfaced: *"Argument-provenance defenses already check
whether tool-call arguments trace to trusted sources — CaMeL, FIDES,
PACT, and Agent-Sentry block or restrict on this basis, and WITNESS's
EXT-only→BLOCK rule is an AIOps-specific instance of the same idea.
Authority-gating agents (AIRGuard, ARGUS, CXI) bind an action to task
authority or LLM-audited evidence, not to corroborated diagnostic
predicates; a memory-poisoning defense (TMA-NM) gates actions on
origin-counted corroboration, but for stored assertions, not an agent's
own RCA claims against provenance-typed telemetry. To our knowledge, no
prior AIOps remediation gate requires channel-diverse system-telemetry
corroboration of the agent's own diagnostic claims plus rules binding
each remediation verb and target to a corroborated claim; WITNESS's
argument-lineage check adapts these existing provenance defenses to
telemetry. This design also sidesteps a documented failure mode:
causal-attribution signals can mistake legitimate tool data for an
attack[20]"* — the last clause citing "Influence Is Not Authority"
(arXiv:2608.29942) as motivation, per the review's explicit
recommendation.

Drop the now-uncited Dantas survey reference (its only citation was in
the sentence being replaced; the template requires every reference to
be cited in the body) and add seven new numbered references: PACT,
Agent-Sentry, AIRGuard, ARGUS, CXI, TMA-NM, and "Influence Is Not
Authority." **Applied directly** to both delivered `.docx` files
(the v3-template final paper and the earlier draft) — this file
documents why, as with every other change above.

**Not applied** (flagged as optional/lower-priority in the review, and
held back to control page growth against the v3 template's 3-page
technical-content limit): GuardedAct as a risk-gating AIOps contrast,
and "Stored Is Not Supported" (arXiv:2609.02127) as further mechanism-1
supporting evidence. Both are easy follow-on additions if space allows.

## 10. Title changed — "Unforgeable" was an overclaim against what's actually attested

**Current text:** *"WITNESS: Unforgeable Corroboration for Safe Autonomous
Remediation by AI Operations and Security Agents"* (appears twice: the
cover-page title and the abstract-section heading).

**Why this is unsafe:** an external strategic review flagged this as the
single highest-priority correction. "Unforgeable" is a claim about the
evidence itself — that a SYS channel's reading cannot be forged. Nothing
in this prototype cryptographically attests that a SYS channel wasn't
itself compromised (no signature, no TEE attestation); WITNESS's actual
guarantee is that corroboration is *checked* across channel-disjoint,
dependency-diverse sources, not that any individual source is
unforgeable. This README made the same distinction from the start (see
"On the title" in [`README.md`](README.md#the-central-invariant)); the
abstract's title had not caught up.

**Change:** replace both occurrences with *"WITNESS: Provenance-Corroborated
Admission Control for Safe Autonomous Remediation by AI Operations and
Security Agents."* Cryptographic attestation of SYS channels remains
explicit future work (README Roadmap item 2), at which point a stronger
title claim would actually be earned. **Applied directly** to both
delivered `.docx` files.

## 11. Hypotheses (H1, H3) — wording no longer outruns the evidence, and now cites the new evaluation corpus

**Current text:** H1 was "confirmed" using only the small-N live-pilot
numbers (7 gated trials total across two agents); H3 ("SOC utility beats
telemetry masking") was stated as a flat, "confirmed"-adjacent claim
with no measurement behind it at all — an architectural argument dressed
as a finding.

**Why this needed fixing:** the same external review flagged this
directly: "confirmed" is too strong a word for n=7, and H3 was untested,
not confirmed. Overclaiming hypothesis strength is exactly the kind of
thing a reviewer catches and a paper's credibility doesn't recover from
easily.

**Change:**
- **H1** now cites two independent lines of evidence instead of one:
  the original live-pilot numbers, *and* the new 138-trial deterministic
  adaptive-attack corpus (`scripts/security_evaluation.py`, 9 attack
  families including the witness-dependency and staleness-replay
  attacks this review also asked for — see item 12 below), both at 0%
  attack success. This is a strictly stronger, better-evidenced claim
  than before, not a weaker one — the fix was in what was cited, not in
  softening the result.
- **H3** is now explicitly labeled *"(H3, architectural — not yet
  measured head-to-head)"* and reworded from "SOC utility beats
  telemetry masking" (asserted as fact) to "SOC utility should exceed
  telemetry masking" (a design argument: WITNESS keeps EXT fields
  visible by construction, masking deletes them) — honest about there
  being no head-to-head utility measurement against an actual masking
  baseline.
- The abstract's closing sentence (previously a single small "legitimate
  values" attack-set result) now also reports the new 120-trial
  legitimate-workload false-hold-rate finding (0%) and the 4-way
  mechanism-ablation result (lineage alone and corroboration alone each
  independently stop a third of a deterministic attack subset; only the
  conjunction reaches 0%) — see item 12.
- "Current status" now says 72 automated tests (was 67, before today's
  5 new dependency-graph/fail-safe tests) plus the 283-trial security
  evaluation corpus.

**Applied directly** to both delivered `.docx` files; no page-limit

## 12. New evidence this session: witness-dependency graph, and a 283-trial deterministic security evaluation

This is new work, not a correction to existing text, so it's
documented here rather than as a change to a specific abstract
sentence (its numbers are folded into items 10–11 above and into
[`README.md`](README.md#security-evaluation-at-scale-the-deterministic-corpus)
directly):

- **Witness-dependency graph** (`TelemetryEvent.dependency_id`,
  `witness_core/provenance.py` and `corroboration.py`): channel-class
  diversity alone was a documented gap — two witnesses can sit behind
  different infra families yet be derived from the same underlying
  measurement (this project's own `docker_stats`/`cgroup_direct` CPU
  witnesses, both reading the same kernel `cpuacct.usage` file, were
  the concrete example already in this README). `dependency_id` is now
  an enforced check, not just documentation: two witnesses sharing a
  declared dependency no longer satisfy the two-witness quorum. The
  live pilot's CPU predicate now needs a genuine third measurement path
  (`docker_top_cpu_pct()`, a different kernel accounting subsystem) to
  admit at all, now that its original two witnesses are correctly
  recognized as non-independent.
- **Fail-safe witness queries**: `WitnessCatalog.corroborate()` now
  treats a raising witness-query call (a real deployment's Prometheus
  client throwing, e.g.) as `NOT_CORROBORATED` rather than propagating
  the exception — closing one more path that could have silently
  skipped a corroboration check instead of failing safe.
- **`scripts/security_evaluation.py`**: a new deterministic evaluation
  harness (no live infra, no LLM) driving the real, unmodified
  `WitnessGate` against 283 trials — 9 adaptive attack families (138
  trials, 0% attack success), a legitimate-workload false-hold-rate
  benchmark (120 trials across all 15 real service names and every real
  K-approved literal, exceeding the review's "100 legitimate trials"
  ask, 0% false-hold), a fail-safe-injection suite (25 trials, all
  correctly held/blocked), and a 4-way ablation study isolating lineage
  from corroboration (100% → 33.3% → 33.3% → 0% attack success across
  no-defense/lineage-only/corroboration-only/full WITNESS, 100% benign
  utility throughout). This directly answers five of the external
  review's Tier-1 items: attack-trial scale-up, the 100-legitimate-trial
  ask, false-hold-rate measurement, the ablation study, and
  adaptive/WITNESS-aware and witness-dependency attacks specifically.
  Full results: `live_env/results/security_evaluation.json`.
- **Formal invariant and threat model**: the admission rule is now also
  stated as an explicit **Corroborated Remediation Invariant** —
  `ADMIT(a) iff (∀ claim: Corroborated(claim)) ∧ (∀ argument: TrustedLineage(argument)) ∧ SchemaValid(a)`
  — plus an explicit attacker-capability table (what an attacker can
  and cannot control), in
  [`README.md`](README.md#the-central-invariant). Not added to the
  space-constrained abstract itself; the abstract's existing mechanism-3
  paragraph already states the same rule in prose ("admitted only if
  all load-bearing claims are corroborated and all argument lineages
  trusted").

## 15. Property-based invariant testing added; test count synced to 104

**New work:** `tests/test_invariant_properties.py` adds 5 property-based
tests (using [Hypothesis](https://hypothesis.readthedocs.io/)) that
check the Corroborated Remediation Invariant against hundreds of
randomly generated `EvidenceStore`/`Claim`/argument fixtures, not just
curated ones — the practical, dependency-free substitute for formal
verification this project's no-paid-tooling constraint allows. On its
first run it disproved an over-strong hypothesized property ("SYS-channel
attestation can only ever remove accepted witnesses relative to
attestation off") with a genuine counterexample, in favor of a
narrower, verified, and more precise one ("no two accepted witnesses
